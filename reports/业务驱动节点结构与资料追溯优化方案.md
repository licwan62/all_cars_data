# 业务驱动节点结构与资料追溯优化方案

编制日期：2026-10-19  
适用范围：all_cars_data 当前业务工作区及其正式交付接口  
文档性质：待实施设计；本文列出的新增台账、追溯接口和业务检查尚未上线  
设计依据：本会话对 pipeline.json、17 个节点的资料、关键逻辑、当前交付与测试/重建结果的分析

## 1. 改造目标与业务验收

项目负责把车型事实、商品资料、市场与客户反馈，转化为可解释的适配、定制、销售和履约资料。节点划分以资料维护责任和业务交付责任为依据。

改造后，日常维护应能直接回答：

1. 某车型的尺寸、结构、车形和匹配尺码分别依据什么资料？
2. 一份资料、一条规则或一次人工修订被哪些输入采用，影响了哪些输出？
3. 资料已经录入，为什么结果仍未变化：未启用、不适用、待判断，还是尚未重算？
4. 一条销售适配范围、定制候选、SKU 或发货数量是如何形成的？
5. 回看旧版结果时，当时的资料、业务决定和计算过程能否还原？

人工负责维护原始资料、业务规则和处理决定；系统负责生成采用关系、结果依据、影响清单和运行证据。维护人不需要手填哈希、Git 版本、运行批次和逐行计算关系。

### 1.1 完成标准

| 验收事项 | 业务判断标准 |
| --- | --- |
| 查结果 | 从任一正式交付的关键结果，能逐层找到输入、采用资料及规则/人工决定 |
| 查资料 | 从任一正式采用资料，能找到实际命中对象、生成结果及未采用原因 |
| 查变更 | 修改资料后，能列出需更新的业务结果与无需更新的结果 |
| 查例外 | 每条例外都有明确对象、原因、依据及有效状态 |
| 查历史 | 旧结果对应旧资料与旧决定，不被当前资料覆盖解释 |
| 查待办 | 缺资料、身份歧义、范围冲突、未重算分别列出并归属到节点 |
| 降低维护负担 | 同一业务事实只在一个归属节点维护；采用清单与结果依据自动生成 |

### 1.2 改造边界

- 保留 data、output、artifacts 的仓库约定，保留稳定业务交付文件名。
- 现有节点目录先保留；仅在独立业务责任确有需要时拆分或调整登记。
- 新交付尚未生成并校验时，登记为 pending，不提前列入 outputs。
- 历史 artifact 保持原字节；新旧身份关系、修订和迁移说明写入新批次。
- 正式运行只消费本节点 data 和已声明上游 output。NAS 公共目录只承担对外发布。
- 自动与按需产线保持现行约定；研究建议通过业务采纳进入正式维护资料。
- pipeline.json 仍由 D2 维护；流水线状态.md 仍只由发布脚本生成。

## 2. 当前问题及其业务影响

以下为本会话前序只读检查和沙箱重建的基线，尚未修复。工作区包含用户已有未提交内容，本文以当前工作区为分析对象。

| 现象 | 已观察到的情况 | 业务影响 |
| --- | --- | --- |
| 资料到达但下游未承接 | 01 的 US 尺寸库 4,383 行；结构审核、编码映射、A0 为 4,378 行。下游缺 9 个当前主键、保留 4 个已移除主键 | 已维护的车型可能未进入销售适配，旧身份仍被沿用 |
| 运行不能完整重现销量 | Chevrolet Cavalier 1984 分配权重缺项，销量节点重建中止 | 尺寸身份变化没有完整承接到销量分配 |
| 尺码存在多值 | A1 当前输出对应运行记录中，US/EU/RU 分别有 10/6,565/2,877 条跨尺码 MULTI 检查记录 | 相同对外识别条件可能查到多个尺码 |
| 部分业务交付未进入总登记 | D2 根节点登记 0 个输出，皮卡子项目已有独立 manifest 和 5 项交付 | 总状态无法完整反映真实业务交付与追溯范围 |
| 正式资料归属不清 | 销量证据、分配权重保存在 cache；部分长期判断依赖旧 output | 资料看似可重建，实际承担正式业务依据 |
| 资料身份与采用关系不完整 | 已有文件哈希、来源映射和部分规则ID，但未统一形成结果到资料的关系 | 能证明文件一致，仍难解释一条结果为什么产生 |
| 待接入与已交付混在一起 | 00、D1、X1 部分交付待产出；X2 没有当前可运行命令 | 容易把历史结果或研究原型当作当前可用业务接口 |
| 历史审核检查失效 | X1 四个测试因引用不在本地的历史批次而初始化报错 | 日常检查依赖历史文件位置，不能稳定验证现行业务 |

需要区分冲突来源：US 的 10 条、RU 的 2,877 条 MULTI 均涉及源原子键对应多个尺码；EU 大部分同样如此。应先检查车型身份和对外表达是否丢失区分信息，再判断压缩是否新增冲突。

## 3. 业务结构：事实、判断、研究、履约分别负责

### 3.1 四个业务环节

~~~mermaid
flowchart LR
    A["车型事实维护<br/>来源、身份、尺寸、结构、车形"] --> C["商品适配与表达<br/>尺码、店铺、适配表"]
    B["市场与客户资料<br/>销量、评价、使用反馈"] --> C
    B --> D["业务选型与研究<br/>代表车型、定制需求、边界建议"]
    C --> D
    C --> E["SKU与履约核对<br/>方案、链接、既成发货"]
    D -. 经业务采纳形成维护决定 .-> E
~~~

该图表达业务关系；实际运行依赖仍以 pipeline.json 中真实消费的输入为准。

### 3.2 资料归属原则

| 资料类型 | 唯一业务归属 | 下游如何使用 |
| --- | --- | --- |
| 车型身份、尺寸事实及身份承接 | 01 | 读取已发布事实及身份承接关系，维护自己的用途对应 |
| 结构与车衣业务分类 | 02 结构审核 | 按精确车型身份读取判定结果 |
| 市场销量及分配依据 | 02 销量评估 | 读取销量及口径，不自行重新估算 |
| 车形及其证据状态 | 03 | 读取或关联分类与证据；证据元数据仍在 03 维护 |
| 商品实测资料、尺码定义与店铺对应 | A0 内的商品资料职责 | 适配计算和店铺转换共同引用同一资料 |
| 适配规则、适配例外 | A0 内的适配判断职责 | 输出匹配结果及采用依据 |
| 评价原文及问题归类 | B0 | 评分和研究引用 B0 的记录与结论 |
| SKU 方案及成员 | D1 | 链接与履约引用实际采用的方案 |
| 既成发货、链接字段对应 | D2 对应子项目 | 方案变化不自动重写历史发货事实 |

同一外部文档可以被多个业务引用。保管原件的节点登记资料，其他节点记录来源关系和自己的提取/判断；不各自维护互相独立的事实副本。若必须保存仓库外证据，按 RunBatch 约定保存必要快照并登记来源。

### 3.3 三项明确的结构调整

**A0：在同一节点内先分开商品资料、匹配判断、销售渠道对应。**

- 商品资料：尺码名称、有效商品尺寸、测量口径、实测/设计/历史资料状态。
- 匹配判断：车型需要满足的规则、边界、白名单与人工例外。
- 销售渠道对应：匹配尺码到店铺发货尺码、平台尺码的映射。
- TRIM 对应：车型版本/配置与具体适配结果之间的对应资料。

四类资料在维护目录和职责上分开，现有 A0 稳定输出保持。资料确有独立维护人、独立更新节奏且被多处使用后，再评估商品资料是否成为独立上游节点。

**D2：以已形成业务交付的子项目作为正式登记单位。**

- 皮卡具有独立资料、运行、测试和稳定交付，目标为正式独立登记节点。
- D2 根目录作为业务容器，不再以零输出代表皮卡业务已验证。
- W 型车、通用发货分析在具备明确输入与交付后分别登记；没有交付时保留待接入状态。
- 子项目正式资料归其自身 data；当前放在容器目录的工作簿需要登记归属，并在实施批次中调整路径。
- 子项目代码按 src/code/scripts 归集；历史父节点及子项目 artifact 保留原位，新 manifest 保留合法来源引用。
- 根节点退役、子节点 ID、release 索引与结构校验的转换在同一结构变更批次处理，避免父子重复发布、重复执行测试或遗漏交付。

**F0、D1、D2：候选方案、业务采纳方案、真实执行分别登记。**

- F0 提供研究候选和待验证任务；尺寸接近不自动等于共版通过。
- D1 维护用于业务执行的 SKU 方案、成员和方案状态。
- D2 维护真实上架、对应和发货事实，引用实际采用方案。
- D2 审核既成发货时，缺少某次候选研究结果不应阻止事实核对；缺少方案依据应明确列为待补依据。
- 不因预设业务顺序强制建立运行依赖。只有实际消费上游 output，才登记对应上游。

## 5. 每个节点的资料结构

### 5.1 目标目录

~~~text
节点/
├─ data/
│  ├─ 节点职责.md             业务问题、资料维护责任、关键口径与例外处理方式
│  ├─ 资料目录.csv            资料身份、出处、用途、范围、状态
│  ├─ 资料/                   原始资料、证据、必要参考
│  ├─ 规则/                   本节点统一执行的业务规则
│  ├─ 例外/                   指定车型、年份、商品的特殊决定
│  └─ 维护决定.csv            仅在现有业务表无法表达修订/采纳时增加
├─ output/
│  ├─ 原有稳定业务交付
│  ├─ 资料采用清单.csv         自动生成的内部追溯接口
│  ├─ 结果依据.csv             自动生成的内部追溯接口
│  ├─ 待处理清单.csv           有相应事项时生成
│  └─ manifest.json
├─ artifacts/
│  └─ 新运行批次/             RunBatch；保存来源引用、决定版本、输出与必要审计资料
└─ src/、code/ 或 scripts/
~~~

目录以业务实际需要创建，不要求每个节点都有相同子目录。先登记现有路径，再逐步整理，避免一次移动所有资料造成业务中断。

### 5.2 人工维护的最小信息

**资料目录：登记材料，不重复登记材料中的业务数值。**

| 字段 | 谁填写 | 要求 |
| --- | --- | --- |
| 资料ID | 首次由系统生成，维护人沿用 | 文件改名不改变身份；整体替换关系有记录 |
| 资料名称、文件位置/外部出处 | 维护人 | 能定位原资料及来源；外部网址不能代替已保存证据的引用 |
| 业务用途 | 维护人 | 计算依据、研究参考、历史停用、说明资料 |
| 适用对象与范围 | 维护人/从资料提取 | 市场、车型、年份、代际、版本、结构、CAB/BED 等；未知保留未知 |
| 资料日期、维护人、状态 | 维护人 | 区分资料时间与录入时间 |
| 替代资料ID | 维护人 | 有替换关系时填写 |
| 内容版本与哈希 | 系统 | 用于绑定该次运行实际使用的内容 |

**维护决定：优先在现有业务表增加稳定记录ID和依据列。**

- 分类判定继续在分类判定表维护；耳位继续在耳位登记中维护；尺码规则继续在规则文件中维护。
- 同一决定不再抄写到另一张通用台账；程序将现有行识别为决定记录。
- 缺少合适业务表时，才新增维护决定.csv。
- 决定最少包含：决定ID、对象范围、处理事项、采用/修订/排除结论、理由、资料ID、维护人、生效状态。
- 涉及替换或撤回时，引用原决定ID，并保留原因和日期。
- 同一资料可支持多个决定；同一决定可引用多份资料。
- 若暂无业务维护负责人，登记为待指定并明确当前维护角色，不虚构负责人。

### 5.3 资料状态与采用状态分别记录

| 维度 | 建议状态 | 解释 |
| --- | --- | --- |
| 资料维护状态 | 候选、有效、被替代、撤回、历史保留 | 说明该资料在业务上的位置 |
| 本次采用状态 | 已采用、范围不符、未启用、被其他决定覆盖、证据不足、存在冲突、尚未接入 | 说明本次运行实际如何处理 |
| 结果交付状态 | 可交付、待补资料、待业务判断、待重算、研究候选、历史冻结 | 说明结果能否用于其声明用途 |

“已登记”不等于“已采用”，“已采用”不等于“已验证适配”。规则文件存在但 enabled=false 时，应显示未启用，不能列为已生效依据。

## 6. 输入输出追溯设计

### 6.1 每条业务依据形成一段可连接的关系

~~~mermaid
flowchart LR
    M["资料与内容版本"] --> D["规则或业务决定"]
    I["本次实际输入记录"] --> U["采用/未采用及原因"]
    D --> U
    U --> O["输出记录与关键字段"]
    O --> N["下游实际采用记录"]
~~~

运行批次、文件来源和哈希用于证明关系绑定了当时真实读取的数据。文件证据和业务关系同时保留。

### 6.2 自动生成的清单

| 清单 | 一行表达的关系 | 主要字段 |
| --- | --- | --- |
| 运行输入记录 | 某批次实际读取哪份输入及内容版本 | 沿用 run.json 的节点、文件、版本、artifact 来源、哈希；补真实消费范围 |
| 资料采用清单 | 一条资料/决定如何作用于一个输入对象 | 采用关系ID、资料ID/决定ID、输入节点/文件/记录键、采用状态、原因、运行批次 |
| 结果依据 | 一个输出关键字段或结果由哪些输入和决定形成 | 依据关系ID、输出文件/记录键、结果字段、输入节点/文件/记录键、采用关系ID、处理说明、运行批次 |
| 待处理清单 | 一个业务问题需要谁处理 | 问题ID、问题类型、对象、资料/决定引用、影响交付、归属节点、状态、处理结论 |
| 变更影响清单 | 本次资料变化会影响哪些业务对象 | 变更资料/决定、受影响节点与记录、处理动作、原因、更新前后对应版本 |

前三类形成基本追溯能力。待处理清单按需生成；变更影响清单在变更时生成，历史明细进入新 artifact 的 extra。

**追溯粒度：**

- 普通透传字段记录输入来源，不重复保存整份上游表。
- 尺寸、结构/分类、车形、尺码、人工例外、SKU 成员、发货数量等关键字段记录具体依据。
- 单一规则作用于一批对象时，可用一条规则关系加对象关联明细，不重复存规则正文。
- 汇总、销量分配、评价归类、压缩和聚簇必须支持多对多关系。
- 关键决定的修改保留前后值或可定位前后版本的引用；不可只写“已调整”。
- 不要求每个普通文本单元格都生成冗余记录，先覆盖影响业务结论的字段。

### 6.3 稳定业务身份

| 对象 | 使用的身份 | 特别要求 |
| --- | --- | --- |
| 车型尺寸记录 | 现有 DIMENSION-ID | 变更后由身份承接关系连接新旧记录 |
| 原始资料记录 | 来源记录ID；缺失时生成受控记录ID | 固定原资料版本与记录位置，行号仅作辅助定位 |
| 规则、人工例外、判断 | 规则ID/决定ID + 内容版本 | 改条件或结论后可查到旧内容 |
| 原始评价 | 评价记录ID | 去重、更正、排除保留关系 |
| 代表车型/研究候选 | 候选或方案ID + 版本 | 选中、排除和采纳分别记录 |
| 压缩适配记录 | 批次 + 产线 + 类型 + 记录序号 | 跨批次通过成员和变更关系承接，序号不充当永久身份 |
| SKU | 稳定 SKU 身份及方案版本 | 名称可变，身份和承接关系保留 |
| 展示链接 | 链接记录ID | 一个实际 SKU 可对应多条展示链接 |
| 发货事实 | 发货记录ID + 业务单据/明细引用 | 无单据号时先生成内部ID，不伪造外部单号 |

DIMENSION-CODE 不承担唯一车型身份。同名车型跨市场、代际、年份或车身版本不得仅凭名称合并。

### 6.4 身份拆分、合并后的承接

01 维护拟新增的身份承接接口，衔接现有来源映射及 EU_ID迁移。目标字段为：关系ID、旧ID、新ID、关系类型、范围、决定ID、依据、有效日期。

- 一对多拆分：分别说明每个新记录的来源；销量、评价、TRIM 等用途由各归属节点判断如何分配，不把旧值全量复制到每个新记录。
- 多对一合并：保留所有来源及合并理由；下游明确去重或汇总口径。
- 撤回记录：保留撤回依据与替代对象；没有替代时保持空，不猜测承接。
- 同一身份的事实修订：保留事实内容版本和修订决定，不能因 ID 未变而遗漏影响检查。

### 6.5 引用、保存和对外发布

- 当前追溯接口放 output，并在 pipeline 登记；旧版在新 artifact 留存。
- 上游已发布文件引用来源，不再次复制；已提交 data 按哈希与 Git 版本引用。
- 未提交资料、仓库外资料等按 RunBatch 约定保存必要快照。
- 大明细存 extra 并 gzip；结果依据只保存关系和必要解释，不复制整份业务输入。
- 历史 artifact 及归档位置仅供审计、还原；不能成为当前运行的默认输入。
- 对外发布采用明确的业务交付清单。资料采用、结果依据和内部待办即使是 CSV，也不自动公开。
- 实施时先补公共发布清单，再把内部追溯 CSV 注册到 output，避免现有“遍历 CSV 发布”造成误发。
- F0 继续只交付业务 Markdown；机器追溯清单属于内部辅助接口，不能恢复为已取消的业务 CSV 交付。

## 7. 资料修改后的业务处理流程

### 7.1 普通资料维护

1. 在归属节点录入或修订资料/现有业务表，沿用资料ID和决定ID；说明新增、修订、替代或撤回。
2. 系统列出对象范围和预计影响：哪些车型、规则、适配记录、SKU 或报告会受影响。
3. 本次运行冻结实际输入与维护资料版本，生成候选结果、采用清单和差异说明。
4. 对照节点的业务必查项处理问题。已经授权、符合既定规则的维护按既定规则执行；需要新业务判断时形成可审阅的对象和差异清单。
5. 通过后整组提交业务结果、追溯清单与 manifest，再发布；失败保留旧的稳定交付。
6. 自动主链按实际受影响输入重算；按需节点列出待刷新对象，保留其旧版输入依据。

### 7.2 研究建议的业务采纳

研究节点给出对象、证据、建议值/方案、适用范围和风险。归属业务节点采纳后，在自己的 data 形成维护决定，并登记研究来源。

例如 X1 的尺寸修订由 01 接纳，X2 的尺码边界建议由 A0 接纳，F0 的候选方案由 D1 接纳。自动运行读取已接纳的维护决定，不反向读取按需研究的 output 或 artifact。

若研究资料已发布，采纳登记引用其节点、版本和证据。需要持续参与正式计算的事实/参数由归属节点在 data 明确维护；研究报告只作来源说明时不在每次计算重新读取。

### 7.3 零命中与未采用

- 启用资料没有命中输入时列明原因：适用对象尚未入库、范围改变、已被替代或确实本批无适用记录。
- 零命中不一律判失败。原计划应命中的对象未被命中，才列为必须处理事项。
- 研究参考、历史停用和说明资料不要求影响输出。
- 采用关系不得根据“文件放在 data”或“文件有哈希”推断；必须来自实际读取与匹配过程。

### 7.4 更正与撤回

- 事实错误通过更正记录连接原事实，不抹去历史交付依据。
- 撤回规则或证据时，列出仍依赖它的当前结果，区分需重新计算和需重新研究。
- 历史发货按真实更正关系处理，不能因当前适配或展示名称改变而自动重分配历史数量。
- 旧批次使用旧依据；当前查看旧结果时显示其历史适用范围和后续更正，不用新规则覆盖解释旧决定。

## 8. 变更类型与后续动作

| 业务变更 | 首先维护的节点 | 必须检查的范围 | 自动/按需处理 |
| --- | --- | --- | --- |
| 新车型、年份、尺寸修订 | 01 | 身份承接、结构/车形、销量用途、编码、适配及销售范围 | 自动主链更新；B/C/D/E/F/X 按需待刷新并列影响 |
| 结构或业务分类改变 | 02 结构审核 | 车形兼容、适配规则、压缩表达 | 自动主链更新；相关按需结果待刷新 |
| 车形证据/结论改变 | 03 | 车形结果及实际消费该字段的适配判断 | 仅按实际消费更新；不能因标签变更自动宣布实测适配 |
| 销量事实或分配改变 | 02 销量评估 | 总量守恒、A0 销量、压缩销量和业务排序 | 自动数据主链更新；代表、定制等按需待刷新 |
| 商品实测尺寸或适配规则改变 | A0 | 受影响候选、匹配/不匹配、店铺可用商品 | 自动更新相关全量和压缩；相关业务分析待刷新 |
| 店铺或平台尺码对应改变 | A0 | 发货尺码、映射唯一性、对应产线压缩 | 更新实际受影响店铺/平台；真实历史发货保持原依据 |
| 新评价或问题修订 | B0 | 去重、归类、耳位/皮卡问题汇总 | B 线按需更新；F0 等待有需求时刷新 |
| 定制方案采纳 | D1 | 方案状态、成员、SKU 身份及适配依据 | D 线按需更新；不直接改 A0 规则 |
| 新发货或发货更正 | D2 子项目 | 事实数量、实际 SKU、链接映射及更正承接 | 对应子项目按需更新；不触发车型资料重算 |
| X/F 研究完成 | 资料归属节点形成采纳决定 | 建议适用范围与被采纳内容 | 研究完成本身不触发自动主链；已采纳资料变化按归属节点处理 |

正式运行依赖及触发类型继续以 pipeline.json 为准。影响分析可以提示业务关联，不能把“可能有关”自动添加为运行依赖。

## 9. 各业务环节的交付必查项

| 业务环节 | 交付前必查 | 无法满足时的业务处理 |
| --- | --- | --- |
| 尺寸事实 | 来源与单位明确，身份/版本区分足够，合并拆分有依据 | 保留候选或标记待核实，不补猜尺寸 |
| 身份承接 | 应承接记录全部有对应，撤回有说明 | 不把下游标为已承接当前资料 |
| 结构分类 | 改动有判定，职责外字段不被改写 | 输出待判定对象与依据冲突 |
| 销量 | 市场/期间/来源类型明确，分配完整且守恒 | 缺失、代理、估算、零值分别表达；分配不完整不发布新分配 |
| 车形 | 证据与对象对应，状态真实，继承范围有据可查 | 保留 INFERRED/UNKNOWN/CONFLICT 等状态；不升级可信等级 |
| 商品匹配 | 有效商品资料、采用规则、例外及未匹配原因可查 | 无唯一适配依据时保持候选或待判断 |
| 压缩适配 | 对真实原子的尺码表达无新增冲突、覆盖和销量归属可核对 | 区分原有歧义和新增歧义；不得用“已存在”代替业务处置 |
| 合理扩张 | 能区分真实车型年份与表达扩张 | 不将缺少原子事实的年份宣传为已验证适配 |
| 客户反馈 | 评价可回查，去重及排除可解释，适用范围明确 | 不把无样本记为无问题 |
| 定制需求 | 样本量、市场/年份范围、评分依据可查 | 保留数据不足；不能把某市场反馈默认为全球适用 |
| 选型/定制研究 | 候选成员、取舍、待验证任务可查 | 维持研究候选，不等于共版或打样通过 |
| SKU/链接/发货 | 实际 SKU、方案成员、展示链接、事实数量分别有身份 | 数量不能因链接数量变化而重新摊分；差异形成核对项 |

允许按业务用途发布明确的多候选结果，但不能把未解决的多尺码歧义发布为“已确定的唯一适配”。历史例外必须有维护决定，说明用途和适用范围。

## 10. 业务状态与维护视图

### 10.1 三个日常视图

| 视图 | 维护人能看到什么 | 支持的操作结果 |
| --- | --- | --- |
| 查车型/商品/方案 | 当前结果、依据、候选、例外、待处理项、历史变化 | 能解释结果，定位缺资料或错误判断 |
| 查资料/决定 | 内容版本、适用范围、实际命中、未采用原因、受影响交付 | 能确认维护是否生效，决定是否修订 |
| 查待办/变更 | 归属节点、影响对象、原因、建议处理、是否已重算 | 能安排业务维护顺序 |

首期可用现有 CSV、Markdown 和命令生成这些视图，无需先建设新网站或数据库。

### 10.2 必须展示的业务指标

| 指标 | 定义与用途 |
| --- | --- |
| 关键结果追溯覆盖率 | 具有有效输入与判断依据的关键结果数 / 应追溯关键结果数；按节点公布分母范围 |
| 正式采用资料登记完整率 | 已登记资料身份/内容版本的正式采用资料数 / 本次正式采用资料数 |
| 维护决定执行情况 | 已采用、应命中未命中、未启用、冲突、待判断分别计数 |
| 身份承接完整率 | 已完成承接或明确处置的应承接对象数 / 应承接对象数 |
| 适配问题 | 无可用尺码、歧义候选、人工例外、缺少商品资料分别计数 |
| 证据质量 | 候选/推断/有证据/已验证分别统计，几何证据状态与实测适配状态分开 |
| 反馈覆盖 | 有有效反馈样本的对象占比及样本量；缺失不计为低需求 |
| 履约核对 | 输入数量、分配数量、差额、未匹配与重复归属数量 |

试点要求关键结果追溯覆盖率和正式采用资料登记完整率达到 100%，身份变更无未说明遗漏。此为改造验收目标，不代表当前成绩；全库扩展时明确历史资料未核实范围，不伪造补齐。

### 10.3 当前需保持可见的口径限制

- EU 全量表销量为零占位，不能解释成市场无销量。
- RU 销量为 Auto.ru 在售样本代理，不能与 US 销量直接合并比较。
- COVER_SHAPE 当前分析基线为 INFERRED 44,589 条、PROBABLE 2,767 条、VERIFIED 0 条；标签非空不等于适配验证。
- B1 当前基线为 7,479 个车型键中 143 个有评分，不能将其余空值当作低定制需求。
- 已有人工决定但历史原始证据未核实的资料，明确标记，不补造来源。

## 11. 结构迁移与交付连续性

### 11.1 迁移步骤

1. 先登记节点职责、资料归属和现有文件位置，不移动文件，不改变结果。
2. 给现有资料及决定建立稳定ID，补充引用，不重写既有 DIMENSION-ID 或业务编码。
3. 用新批次生成追溯候选，先与原有业务结果对照；资料变化导致的业务差异单独列出，不要求强行保持旧错误。
4. 通过试点后登记内部追溯正式接口，调整公共发布清单。
5. 按节点逐步整理 data，变更文件引用并验证；每次结构变更单独可审阅。
6. 对应业务正式接入后，再更新 pipeline 的输入文件范围、outputs/pending、职责说明与节点状态。

### 11.2 输出与追溯一起交付

- 同批次完成业务表、采用清单、结果依据及必要待办，再提交整组稳定输出。
- 发布时核对本次真实输入与规则内容；不能仅凭发布时读取的最新上游 manifest 更新使用版本。
- 结果内容未变但依据变化，也要保存新的业务依据版本；相同结果字节继续引用既有 artifact。
- 当前资料版本发生变化但没有成功重算时，显示待重算或按需待刷新。
- 旧按需结果继续保留当时依据，不能改写为使用当前资料。
- 整组提交失败时恢复上一完整交付，避免业务表与依据处于不同版本。
- 版本撤回使用已有完整批次，并记录撤回原因和影响；历史批次不修改。

### 11.3 与现有运行设施的衔接

现有 RunBatch、manifest、trace、verify 和发布脚本继续作为基础：

- RunBatch 记录实际输入、维护资料内容版本及自动关系文件；计算前后核对输入未被并发替换。
- 发布脚本以成功运行证据为依据，核对实际输入、决定内容、关键业务检查与输出。
- 追踪脚本增加业务承接和关键依据检查；新上游交付、内容修订、资料撤回都能识别。
- 验证脚本覆盖正式子项目与真实输出；没有登记交付时不能显示交付已验证。
- 同时区分沿用旧结果的兼容重建与不预置旧 output 的首次构建，识别依赖旧结果才能运行的问题。
- 各节点历史判定逐步移入自身 data；自身 output 可以用于差异比较，不能成为未登记的事实或决定来源。

## 12. 实施工作包与依赖顺序

工作包以可验收的业务闭环为交付单位；不以目录搬迁数量或代码拆分数量衡量完成。

| 顺序 | 工作包 | 业务责任角色 | 具体交付 | 完成条件 |
| --- | --- | --- | --- | --- |
| 0 | 资料与责任登记 | 各节点维护人；D2 汇总节点合同 | 17 节点职责、资料目录草案、资料归属/重复/缺证清单 | 每份实际采用资料有归属；历史/研究/说明资料可区分 |
| 1 | 车型修订承接试点 | 01、结构审核、销量、编码、03、A0/A1 维护人 | 以 Countryman JCW 2018 等对象打通来源、身份承接、采用、结果及影响查询；处理 9 缺失/4 残留 | 当前身份完整承接，销量分配可运行，未采用和结果变化可解释 |
| 2 | 适配歧义处置试点 | 01、A0、A1 维护人 | Jaguar XJ 等歧义对象的来源分析、区分字段/决定、候选表达与检查规则 | 每个问题有处置；压缩不新增歧义；未确定结果不冒充唯一适配 |
| 3 | 皮卡履约试点与子节点登记 | D2 皮卡维护人；D2 维护 pipeline | 子项目正式合同、发货记录ID、SKU/链接/事实追溯、数量核对 | 业务总登记覆盖实际交付；按事实归属核对总量，不按展示链接重摊 |
| 4 | 反馈与业务选型追溯 | B0/B1/C1/F0 维护人 | 评价→问题→评分；适配范围→代表选择；成员→定制候选与待验证任务 | 样本及适用范围可查；研究候选与采纳/验证分开 |
| 5 | 研究采纳闭环与历史整理 | E0/X1/X2 及采纳节点维护人 | 异常处置、研究建议采纳去向、现行规则适配、历史冻结/退役清单 | 不反向修改上游；按需研究不成为自动链隐式依赖 |
| 6 | 全节点推广与维护减负 | 各节点维护人；运行维护角色 | 正式追溯接口、三类维护视图、分范围重算、归档与资料说明 | 全部正式关键结果可追溯；资料只维护一处；失败不破坏完整交付 |

发布输入核对、公共发布清单、整组提交等支持能力，随试点所需建设。先完成本业务闭环，再推广到其他节点。

### 12.1 每个工作包必须提供的材料

- 本次处理的业务问题、对象范围和维护资料。
- 新增或修订的事实、规则和决定。
- 输入到输出的具体样例，以及正向影响查询。
- 原结果与新结果的差异；无差异时说明资料采用情况。
- 未解决问题、归属节点和可用范围。
- 运行证据、适当测试与业务验收结果。

不为未知历史依据编造资料；不把只完成文件登记算作追溯闭环完成。

## 13. 三个首批验收场景

### 13.1 官方车型资料已进入尺寸库

对象：MINI Countryman JCW SUV 2018 US。

业务操作：录入或修订该车型证据并生成结果。

必须能查：

1. 官方资料及其年份、市场、车型版本范围。
2. 01 输出记录及尺寸字段的具体来源。
3. 结构分类、车形判断各自的决定与证据。
4. A0 实际采用的尺寸、规则、候选和最终结果。
5. A1 销售范围是否覆盖该对象；没有覆盖时的明确原因。
6. 哪些按需报告或 SKU 方案需要时再刷新。

验收：不能出现“01 已有该对象，但下游遗漏且仍标为已承接当前资料”。此处不预设该对象应匹配哪个尺码。

### 13.2 相同对外条件对应多个尺码

对象：Jaguar XJ Sedan 1988 等已有问题。

业务操作：从多尺码结果查询来源。

必须能查：

1. 各尺码来自哪些源尺寸记录、车型版本与规则。
2. 原始身份是否已冲突，还是整理销售范围时丢失了区分条件。
3. 业务决定如何区分、保留候选、撤回或补证。
4. 销量如何归属，避免重复计算。

验收：不能通过随意选最大/最小尺码或改变检查定义隐藏问题；已确定结果必须有区分依据，多候选明确标示。

### 13.3 真实发货与展示链接一对多

对象：D2 皮卡已存在的实际 SKU、发货事实与展示链接。

业务操作：查询某条发货数量及其展示去向。

必须能查：

1. 原始发货记录、日期、数量及事实更正关系。
2. 实际 SKU、业务方案版本和成员依据；没有方案时列待补。
3. 对应展示链接和链接字段生成依据。
4. 展示链接增加或改名后，原始发货数量仍保持事实归属。

验收：发货输入总量、分配总量和差额可核对；多个展示链接不导致重复累计或重新摊分。
